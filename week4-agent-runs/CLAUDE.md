# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Week 4 of the course repo (`ai-agent-design-fall-2026`): a lab comparing AI agent setups. The three setups are Claude Code + Claude Opus 5.5, pi + Opus 5.5, and pi + Gemma 4 on local Ollama. It has no build, no dependencies and no test suite. Each week's folder is self-contained, and later weeks copy what they need instead of importing from here, so this week stays reproducible for students.

- `report.py`: a single-file, stdlib-only Python 3 script that parses agent session logs (`.jsonl`) and writes a side-by-side Markdown report.
- `run.py` + `prompt.txt`: the launcher that produces the runs `report.py` reads. See "Running the agents" below.
- `runs/<setup>/run<N>/stack.md`: each run's write-up of its stack's layers, from interface down to physical facility, as `prompt.txt` asks. These are agent output, not project files.

## Running the script

```sh
python3 report.py                            # pick a runs/ folder per setup (Claude Code, pi cloud, pi local)
python3 report.py runs/A runs/B runs/C        # those setup folders, one column each
python3 report.py a.jsonl b.jsonl            # writes report.md and prints it
python3 report.py a.jsonl b.jsonl --md -     # stdout only
python3 report.py a.jsonl b.jsonl --full     # detailed report: every counter and event
python3 report.py a.jsonl --label A --price A=IN,OUT[,CACHEWRITE,CACHEREAD]
```

Log sources: Claude Code writes to `~/.claude/projects/<project>/*.jsonl` and pi writes to `~/.pi/agent/sessions/`. `main()` is the authoritative CLI.

## Running the agents (run.py)

```sh
python3 run.py claude            # one interactive run; the prompt is sent for you
python3 run.py pi --auto 5       # five unattended runs
python3 run.py claude --model claude-sonnet-5 --effort high
```

- Each run gets a new folder `runs/<setup>/run<N>`, with `runs/` next to `run.py` (`RUNS`), whatever folder it's started from. The setup is `<harness>-<model>-<effort>`, plus the provider for pi when it isn't the model's own home (`HOME_PROVIDERS` = anthropic, google, ollama are left out): `runs/pi-opus5.5-medium/run1`, but `runs/pi-openrouter-opus5.5-medium/run1` (in the provider part, `.` replaces `-`, e.g. `google.vertex`). `--dry-run` prints the folder and command without running anything; use it to test changes instead of launching real runs. Inside the model part, `.` replaces `-` and `:` (`model_slug`: `claude-opus-5-5` → `opus5.5`, `gemma4:26b` → `gemma4.26b`), so dashes only separate fields. A new model or effort starts its own series at run1. Model and effort are always passed explicitly, never left to a CLI default, so the folder name matches the log (Claude Code logs `effort` on assistant lines, pi logs a `thinking_level_change` event).
- Manual and `--auto` runs are meant to be interchangeable. They use the same prompt, settings and permissions, and the only difference is `-p`. Claude Code runs with `--permission-mode dontAsk` plus the `CLAUDE_TOOLS` allowlist, so no one answers a permission prompt. Claude Code still runs read-only shell commands like `whoami` without asking, and denies changing commands like `touch` unless they're allowlisted.
- Context isolation: run folders sit inside this project, below this CLAUDE.md, so Claude Code runs with `--safe-mode` and pi with `--no-context-files`. Both were verified with a canary CLAUDE.md. `--safe-mode` also turns off the user's own CLAUDE.md, skills, MCP servers and hooks, which keeps runs comparable across machines.
- The prompt has to come before `--allowedTools` in the Claude command line. That flag takes every value after it, including a trailing prompt.
- For Ollama models, `warm_up` checks through Ollama's API that the server is up and the model is pulled, and prints the fix (`ollama serve`, `ollama pull …`) if not. Then it loads the model before the first run, so load time isn't counted as the agent's latency.
- pi can use cloud models: `--provider anthropic|google|google-vertex` plus a required `--model`. `check_pi_login` runs `pi auth check --provider … --model … --json`, which reports readiness without printing secrets, and stops with `/login` instructions if pi isn't logged in. Credentials come from pi's own `/login` (stored in pi's `auth.json`). The README's default is an Anthropic API key, with OpenRouter (one key, many models) and a direct Gemini key as alternatives. The account login ("Anthropic (Claude Pro/Max)", OAuth) is mentioned only as a footnote. A Claude plan doesn't cover pi: Anthropic bills third-party apps to paid "extra usage", and without it the API returns 400 "Third-party apps now draw from your extra usage". Gemini has no account login in pi, only an API key or Vertex. Don't rely on exported `ANTHROPIC_API_KEY`: Claude Code would pick it up too and bill it instead of the user's plan. pi's model IDs come from its catalog (`pi-ai/dist/providers/data/*.json`), and `pi --list-models` only lists providers that are logged in.

## How report.py fits together

- **Run picker** (`pick_logs`): with no arguments, the script asks for one setup folder per entry in `SETUP_PICKS`, in lab order: Claude Code, pi with a cloud model, pi with a local model. That order puts the controlled pairs in neighboring report columns. `run_logs` scans both log roots once and keeps sessions whose working folder is a run.py run folder (`run_parts`: `…/runs/<setup>/runN`) that still exists, newest log per folder. So a live conversation or another project never appears, and deleting a `runN` folder drops that run. pi logs are split into cloud or local by the provider in their `model_change` event (`LOCAL_PROVIDERS` = ollama), which `run_summary` reads before the first prompt. A setup with no folders exits with the `run.py` command that makes one. With no terminal, it prints the folders and exits 0. On the command line, `arg_groups` turns a setup folder into all its runs, a `runN` folder into one run, and a `.jsonl` file into one column.

- **Format detection** (`detect`): each file is sniffed as either pi or Claude Code. pi logs have `type: "session"` or `type: "message"` with `message.role` in assistant/user/toolResult. Claude Code logs have top-level `type: "user"|"assistant"`. Each format has its own analyzer, `analyze_pi` and `analyze_cc`. Both return the same `OrderedDict` shape (tokens, tools, files, thinking, final text, and a `timeline` of `(offset_sec, who, kind, detail)` tuples), so reporting code doesn't need to know which format it came from. Line shapes the analyzers don't recognize are skipped, not treated as errors.
- **Pricing**: `PRICES` is an ordered substring-match table, and the first match wins, so more specific model names have to come before general ones (`fable-5-1` before `fable-5`). A `--price` flag given with only two numbers fills in cache write as 1.25× input and cache read as 0.1× input. `is_local` treats Ollama-style `name:tag` models as unbilled ($0). Any `totalCostUSD` a harness logs is reported next to the computed cost and doesn't replace it.
- **Labels and headers**: in the default report, columns are headed `<harness> · <model>`. `auto_label` builds the shorter `<harness>+<model_short>` (for example `cc+opus-5`), which is the key `--price` matches and what `--full` uses as column names. A `--label` replaces both. `unique` gives duplicates `-2`, `-3` suffixes.
- **Throughput**: each analyzer records `spans`, one `(request sent, reply logged, output tokens)` per model call. Claude Code doesn't log the send time, so a call is taken to start at the last user or tool-result line before it and end at its last content-block line. pi stores the send time in `message.timestamp` (epoch ms) and the end time in the line's `timestamp`. The wait includes the model reading the prompt, so throughput is lower than the pure generation speed.
- **"How good are the results?"** (`output_checks`): rule-based grading of the `stack*.md` write-up each session produced, shown as a second table in both report modes whenever at least one session wrote one. Both analyzers record `writes` through `record_write`: Write/Edit tool calls, plus `cat > file <<EOF` heredocs in Bash, which is how weaker models often write files. The checked text is the last full-file write taken from the log, so later edits on disk don't change the grade. The file on disk is used only when the session edited the file in place. `stack_layers` handles three layouts, tried in order: a table with an Owner column, one heading per layer (sections like Summary/Caveat/Limits are skipped), and one top-level list item per layer. A layer passes the owner or source check when it has a non-empty `Owner:` or `Source:`/`Basis:` entry, and a link anywhere in the layer also counts as a source. `mark` puts ✅ on a check when every layer passes, ⚠️ when at least half do, and ❌ when fewer than half do or the file is missing. Rows are worded as the prompt's requirements (`RUBRIC_ROWS`), and word count is shown without a mark. The whole rubric block is specific to this prompt: for a new assignment, copy it and change `STACK_FILE`, `RUBRIC_ROWS` and `stack_checks`. File names link to the write-up relative to the report, or stay plain text when the file is gone.
- **Groups and aggregation**: `main` turns the input into groups, one per report column: a setup folder's runs, or each command-line log on its own. `simple_report` and `output_checks` take groups. A one-run group renders exactly as a single run always did, which is checked by diffing against the pre-grouping output. Several runs show `spread` (median, with lowest–highest in brackets), cost per run plus the total, and in the results table `group_checks` counts runs that passed each check (`stack_facts` holds the per-run numbers). `--full` flattens groups back to one column per run.
- **Default report layout** (`simple_report`), aimed at teaching evaluation: the measured table, then "How good are the results?" (the output checks), then a blank "Your evaluation" table with three judgment questions for students to fill in, then Traces: each run's log file name as a link, followed by its steps as a Time/Who/Did/Detail table in a collapsed `<details>` block. Recorded reasoning text appears only in `--full`.
- **Two report paths**: `simple_report` is the default, a readable summary. The `--full` branch inside `main()` builds the exhaustive table. A new metric needs to go into both paths if it should show up in both.
